# 深色 token 补齐 —— 喂给 LLM 的指令（设计师直接复制全文）

> **本指令已完成使命，转为存档**：深色补齐任务已于 2026-09-22 闭环（设计师交付统一双主题规范，工程已集成并验收，见 `dark-theme-intake.md` 终态记录）。后续新增 token 或调值不再走"深色补齐"流程——统一表的 Light/Dark 两列成对维护，改值直接改 `design-language/样式Token/设计系统.md` 后重跑生成器。下文仅作历史方法记录。

---

你是一名设计系统工程师。任务：为 GTS 设计系统补齐**深色主题**的语义 token 值表。

## 输入

- 附件 1 是真值源：所有浅色值、token 命名与语义都在里面。深色值必须与浅色值**同表同 token 名**对位。
- 附件 2 的 §B 是逐组状态清单（已补齐的组标注 ✅），本次只做剩余项。§A.2 是工程约束。逐项完成。

## 任务

深色表已交付一部分（品牌/文本/图标/边框/背景/功能色/图表深色序列/告警状态色，见真值源 §1.2D）。本次只补**剩余缺口**：

1. 补齐剩余组的深色值（组号对应附件 2 §B）：
   - 第 6 组 填充色 8 项（color-hover / color-select / color-fill / color-fill-subtle / color-fill-disabled / color-fill-disabled-subtle 等）；
   - 第 8 组 表格色 3 项（表头 / 斑马纹 / 表格边框）；
   - 第 9 组 投影 shadow-1..6 深色值（几何可与浅色一致，只调颜色与透明度，逐条显式给出）；
   - 第 12 组 frost 深色材质参数（或给出"深色是否启用 frost"的明确规则）；
   - 深色图表 accessible 序列（11 色的无障碍变体）。
2. 正式化工程回填的 10 项（见附件 2 §B "工程回填待设计师正式化"表）：认可即录入真值源；要改给显式新值并附理由。正式化后工程侧从生成器回填表删除。
3. `--ux-mix-base` 深色表面色：工程暂按背景容器色 #191919 取值；如另有指定值请给出。
4. 第 10 组（基础色板 13 色×10 档深色变体是否整表提供）：列出 2–3 个选项及利弊，**留给设计师裁决**，不要替他决定。
5. 悬停/按下/禁用/获焦等状态色：给出显式值并附一句取色理由（从哪个基础色、什么关系），供设计师逐个确认。

## 输出格式（严格遵守）

- 按组输出 Markdown 表格，列头与真值源一致：`Token | 用途 | 浅色 | 深色`。
- Token 名与真值源**逐字一致**（含大小写、连字符），禁止发明新 token 名、禁止改名、禁止合并。
- 每组表格前一行注明对应真值源章节号，方便设计师直接粘贴回原文档对应小节。
- 不输出任何 CSS/代码/工程文件。只输出值表。

## 深色取值约束

- 深色是一套整体协调的 ramp：先定基础面（背景 bg-1..5、文本 5 级、混色基底），再对位组件语义组；禁止逐组孤立取色导致组间断裂。
- 文本/背景对比度自检：正文级 ≥ 4.5:1，次要文本 ≥ 3:1；禁用态除外但仍需可辨识。
- 状态色必须是显式值（不允许"较浅 10%"这类描述）；候选值之间保持色相一致、明度关系稳定。
- 深色阴影：几何可与浅色一致，只调整颜色与透明度，并在表内明确给出。
- 不确定的值宁可标注 `待定` 并说明原因，不要编造。

## 产出后的流程（写给你参考，不要输出这部分）

设计师将值表粘贴回真值源 → 工程侧跑 `gen-tokens.mjs` 生成 dark 皮肤 → 构建门禁（缺 token 即报错）→ 浏览器深色冒烟。验收标准见附件 2 §C。
