# GTS Skill 审查与最小改进 Spec

日期：2026-10-31
状态：待实施评估；本文件替代原优化方案，不授权直接修改 skill
适用对象：skills/gts-ep-coder

## 1. 目的

判断 GTS 是否存在值得解决的具体问题，并只实施收益明确、代价合理的改动。不预设必须优化，也不以文档更短、文件更多或检查更多作为成功标准。

本次依据是对 SKILL.md、编码规则及部分相关文件的静态阅读。尚未完成同题耗时测试、完整脚本审计、浏览器运行验证或预览兼容问题复现。因此，不能断言 GTS 慢，也不能承诺改动后更快。

## 2. 现状与判断

| 观察 | 可以得出的结论 | 不能据此得出的结论 |
|---|---|---|
| 入口、硬约束和代码规则重复描述部分要求 | 存在维护多个表述的成本，值得检查是否不一致 | 重复一定无用，删除一定提高遵循率 |
| 编码前要求完整读取 code-rules.md | 存在固定读取成本 | 这项成本过高，拆分必然更快 |
| 已有定向查资料、上下文复用、按需国际化、图标缓存 | 已有明确的效率设计 | 所有任务都执行得高效，或仍需重做这些机制 |
| 修改任务已跳过 init，文档改动无需 build | 局部修改已有专门流程 | 需要新增另一套修改工作流 |
| 存在针对预览运行时的特殊业务写法 | 预览兼容性对源码选择有约束 | 限制已过时，或适配层可以低成本修好 |
| 当前设置首次验证加最多两轮修复 | 明确控制重复尝试的成本 | 上限过严，或放宽上限一定改善交付 |
| 构建门禁与源码自查是主要交付条件 | 需要准确说明实际检查范围 | 当前构建成功代表交互与视觉已验证 |

## 3. 本轮允许开展的工作

只开展文档一致性审查和验证表述核对。发现具体问题后做最小修改；没有发现问题则保持原文。

### 3.1 规则一致性审查

检查入口与 code-rules.md 中重复出现的导入、样式、数据层、组件拆分、国际化和响应式要求。

每项记录：出现位置、是否一致、是否各有作用、建议保留位置。

处理原则：

- 相互矛盾的表述必须统一，但先确认哪一项是当前有效约定。
- 入口保留简短关键提醒，详细规则保留完整定义和必要示例。
- 只有内容等价、没有额外执行作用的长段重复才删减或改为引用。
- 不以消除全部重复为目标，不改变规则强度和适用范围。
- 不搬迁目录，不新增专题文件体系，不为行数指标压缩内容。

验收：修改前后逐项对照，规则无丢失、无语义改变、引用有效。若只是文字调整，不要求生成页面或增加运行测试。

### 3.2 验证表述核对

对照实际脚本实现，核对文档对 build、自查及其他验证能力的描述。只有存在夸大或含混时才修改。

表述必须区分：

- 构建：实际已实现的编译、依赖及静态规则检查。
- 运行：实际执行过的挂载或具体交互。
- 视觉：实际查看过的窗口尺寸和区域。

不得把构建成功表述成全部运行或视觉正确。也不因此新增默认浏览器门禁、强制检查清单或每次交付的长免责声明。

验收：每项验证能力都能对应实际检查；交付表述不超过已取得的证据。若现有文档已准确，则不改。

## 4. 需要证据才能启动的候选

以下不是本轮实施要求。

### 4.1 是否拆分必读编码规则

启动条件：实际任务记录显示完整读取占据明显成本，或大量无关内容反复进入上下文。

验证方法：相同模型与需求下，对比原版和核心规则加按需专题的候选版。覆盖简单修改、普通页面和复杂页面，同时记录读取成本、总耗时、漏读和规范错误。

决策：只有总成本下降且遵循率未退化才采用。若工具调用增多或规则遗漏增加，保留现有全文必读。没有数据时不拆分。

### 4.2 是否调整修复上限

启动条件：存在具体案例，因两轮上限终止，但当时已有明确、低风险、可验证的修复方案。

分析同时记录：继续修复的成功率、追加时间，以及无进展循环的比例。

决策：证据支持后再讨论例外条件及硬上限。在此之前保留现行规则，不以“有进展”为由自行绕过次数限制。

### 4.3 是否修复预览适配层

启动条件：标准 Vue 写法在真实工程正常，在离线预览中可稳定复现失败，并且特殊写法带来实际维护成本。

先建立最小案例，再评估修复范围、兼容风险和成本。修复后同时检查标准工程与离线预览，并运行受影响的既有回归。

只有验证通过才删除对应业务限制。无法复现或修复成本不合理时保留现有兼容规则，不扩大成运行时重构项目。

## 5. 明确不实施的事项

- 不规定核心规则必须少于100行。
- 不使用未经基线支持的读取量降低30%、启动快20%等硬指标。
- 不重复建设现有局部修改、缓存和按需读取机制。
- 不默认增加浏览器、视觉或维护测试到普通页面任务。
- 不为减少提示词删除关键质量规则。
- 不更换框架、交付形式、设计 Token 或服务层约定。

## 6. 有需要时如何测量

仅在要验证速度或质量假设时开展对比，避免为小幅文字整理投入完整评测成本。

对比需控制模型、需求、环境、工具权限和缓存状态。首次安装与环境已就绪分开统计。用重复样本而非单次结果下结论，报告样本数和波动。

按候选问题选择代表任务：查询页、复杂表单、图表页、截图还原、文案修改、交互修改。无需每个候选都跑全量任务。

记录：到首次写业务代码的时间、到必要检查完成的总时间、资料读取量、修复次数、需求遗漏、额外内容和功能缺陷。

总交付时间与正确性优先于首次写代码速度。更早开始写代码但返工更多，不算收益。接受标准在测试前按业务目标确定，不看完结果后选择有利指标。

## 7. 执行顺序与完成条件

1. 审查重复规则和验证表述，列出具体位置及证据。
2. 对每项给出修改、保留或待验证的结论。
3. 只修改有明确依据的问题，保留现有执行策略。
4. 核对差异、引用及规则完整性；只有影响脚本或流程时执行相应回归。
5. 输出修改清单、未修改原因以及仍未验证的假设。

本轮完成不要求一定产生代码或文档变更。审查发现现状合理并记录依据，同样属于完成。

## 8. 当前结论

已有证据足以支持一次小范围一致性审查，但不足以支持规则拆分、重试策略调整或预览工具改造。最终是否修改，由具体问题和验证结果决定，不由本 spec 预先决定。
