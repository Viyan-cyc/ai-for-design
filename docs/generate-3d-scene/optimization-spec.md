# generate-3d-scene 优化 Spec

版本：实施中 v2
日期：2026-11-02  
状态：第一批（2.1–2.3）、第二批（2.4）已实施；用户确认第二批外部 review 通过。第三批（3.1–3.2）完成文档整理与静态核查，执行收益待实际任务验证；第4–7节未整体实施。证据见第10、12、14、15节。

## 1. 目标与约束

在保留离线预览、源码二开和场景编辑能力的前提下，提高首轮生成稳定性，减少耗时与 token 消耗，并改善首版视觉一致性。不重写引擎。

必须保留：

- 用户模型 → 内网模型 → 合适组件 → 几何降级的选材顺序。
- 默认按需渲染和现有画质设置。
- 统一构建入口，以及最多两轮修复重跑。
- 用户源码、编辑状态和模型原始材质的保护。
- 离线预览与完整源码交付。

明确不做：

- LLM 截图自评、视觉验收、审美修复循环。
- 默认增加浏览器、性能采样或额外验证报告。
- 重写核心引擎、替换离线运行架构。
- 建设大而全的场景模板库。
- 自动添加主题切换、业务面板、动画等未请求功能。

构建检查保证其覆盖范围内的代码正确性；视觉效果由用户查看和反馈。预设只能降低视觉问题发生概率，不能视为视觉验收。

本文路径除特别注明外，均相对 `skills/generate-3d-scene/`。问题依据来自静态 review，实施时须结合当前代码复核并进行相应测试。

## 2. P0：修复正确性问题

### 2.1 交付完整的布局生成输入

问题：`template/scripts/package-delivery.mjs` 的源码目录白名单遗漏 `scenes/`，而 `scripts/scaffolds/compose-scene.mjs` 依赖 `scenes/stage.json`。

改动：

- 将必要布局输入 `scenes/stage.json` 纳入源码交付，不携带 demo 与历史生成候选。
- 检查官方配方所依赖的其他文件是否一并交付。
- 保持缓存、依赖目录和临时文件不进入交付包。

验收：在隔离目录中，从交付 `source/` 运行官方布局生成器，可以生成候选场景，不依赖原工作区。该检查属于 skill 维护测试，不加入每次场景生成流程。

### 2.2 统一保存操作说明

问题：主入口与 `template/src/edit/SaveService.ts` 采用复制修改文本，`references/scene-workflow.md` 仍描述下载 JSON。

改动：

- 当前保存流程统一为：复制修改 → 回传对话 → 校验来源与 before → 回写 → 重建。
- 明确复制成功不等于源码保存成功。
- 旧 JSON 导入能力作为兼容说明，不混入默认流程。

验收：主入口、工作流、生成契约与编辑器实际行为一致，不再出现默认保存下载 JSON 的指引。

### 2.3 修正检索输出契约

问题：`scripts/search-assets.mjs` 内网分支未使用 `--brief`；服务失败与空结果共用退出码。

改动：

- 两种检索来源都支持统一的精简候选结构。
- 精简字段保留 ID、名称、类别、尺寸、单位、三角形数、兼容状态；未知值明确标记。
- 详细信息按需查询，不默认输出。
- 区分有结果、无结果、服务失败。
- 批量查询存在部分失败时，保留逐项状态，不能将失败项解释为无匹配。

验收：使用本地响应样例验证正常、空结果、失败和部分失败；不依赖内网服务，也不增加生成时的请求次数。

### 2.4 修正低帧率动画时间语义

问题：`template/src/scene3d/scene-core/engine/RenderLoop.ts` 每帧 delta 最大为 0.1 秒，低于 10 FPS 时累计动画时间变慢，与按经过时间推进的说明不一致。

改动：

- 明确区分活动期间真实经过时间与需要限幅的模拟步长。
- 保持后台暂停、空闲恢复时不突然跳跃。
- 检查已有回调兼容性后确定修改方式，不直接移除限幅了事。
- 地图外部驱动路径一并核对。

验收：用可控时钟验证低帧率、正常帧率、暂停恢复及空闲恢复；无需截图或 GPU 性能测试。

## 3. P1：精简指令和增量工作流

### 3.1 每条规则只有一个权威位置

| 文件 | 职责 |
|---|---|
| `SKILL.md` | 意图分流、生成步骤、修改步骤、关键边界、阅读路由 |
| `references/generation-contract.md` | 数据字段、接口、生命周期、最小示例 |
| 设计共享规范 | 构图、视觉角色、细节分配 |
| 领域文档 | 领域特有布局和尺度示例 |
| 资产文档 | 接收、确认、检索、下载、注入 |
| 工作流补充 | 仅保留独有内容；无独有内容则合并移除 |

优先去重：检索与降级规则、重试上限、禁止视觉自检、工作区与交付目录、保存与回写、构建覆盖范围。

命名要求统一为：稳定、同级唯一、符合字符约束；新代码推荐 snake_case，不为统一风格重命名既有槽位。

验收：

- 默认阅读链中，同一完整规则不重复展开。
- 保留必要边界，没有因压缩而丢失接口条件。
- 文件引用均有效。
- 用同一计数方式记录改造前后的默认阅读量，不预先承诺节省百分比。

### 3.2 增加明确的局部修改路径

| 修改类型 | 必要操作 |
|---|---|
| 位置、数量、相机 | 修改对应数据；运行源码变化后统一构建 |
| 现有外观 | 修改对应外观；统一构建 |
| 新增对象类别 | 仅检索新增且未覆盖的类别 |
| 模型引用未变 | 沿用已物化资源，不重复下载或确认 |
| 说明文档 | 不构建 |

补充约束：

- 修改已有场景不重新初始化。
- 不重新加载无关领域文档。
- 不覆盖用户编辑过的布局或槽位。
- 已有确认结果的复用以资产未变更为前提。

验收：通过典型修改任务检查执行轨迹，确认没有无关检索、初始化或重复构建。

## 4. P1：用可执行默认值提高首版一致性

### 4.1 在现有外观体系中提供少量语义预设

沿用 `appearance.ts` 和现有材质工具，不新增平行主题系统。

预设覆盖：

- 场景背景、地面、主体、辅助结构和强调色。
- 常见材质角色及其 roughness、metalness 等参数。
- 与当前无实时阴影默认值相容的明暗层次。

边界：不重涂用户模型，不自动切换画质档位，不自动添加换肤 UI，不把精致简化为更多灯光、更高反射或更多几何。

验收：预设可直接用于现有 handler，参数合法、可编辑、无需额外资源服务。视觉是否满意由用户确认。

### 4.2 将相机取景规则落实为可复用计算

先检查现有能力；只有缺失时才补充工具：

- 根据业务对象边界、宽高比和边距计算初始取景。
- 排除无限地面及无关辅助对象。
- 相机观察目标与控制器目标一致。
- 使用已有资产元数据，不为取景重复加载模型。
- 用户明确指定的相机参数优先。
- 不在用户开始操作后突然自动重置视角。

验收：用数值用例检查横向、纵向、高层和偏离原点的布局能落在预期视锥范围内。此项只解决几何取景，不声称能判断最佳构图或遮挡。

## 5. P2：谨慎扩展复用资产

### 5.1 从已有重复实现提取组合

不先建设完整场景库。仅选择实际反复出现、已有可用实现的组合做试点。

每个组合提供：适用与不适用说明、单位、原点、朝向、占地、参数及默认值、可编辑粒度、最小注册与数据示例。

组合复用不得绕过模型优先规则，也不得强迫用户采用模板数量和布局。

继续扩展的条件：试点能减少生成代码或返工，且接口阅读成本低于直接编写成本。未证明收益则不扩大。

### 5.2 按需引入安全复制工具

可参考 `skills/gts-ep-coder/scripts/copy-components.mjs` 的通用机制：只复制选中项、全部目标预检、相同内容复用、不同内容报冲突、路径检查和独占写入。

适配 3D 的多文件依赖，移除 EP 专用逻辑。不默认覆盖 `scene-profile` 或 scene-data。如果现有复制方式已经足够，则不新增工具。

## 6. 维护清理

### 6.1 处理验证缓存遗留模块

先确认 `scripts/lib/verification-cache.mjs` 在整个仓库中的调用关系。

- 无调用且无保留用途：删除遗留实现与引用。
- 有实际用途：补齐 JS、CSS、JSON 等输入覆盖，修正原子写入说明或实现。
- 本轮不为了提速强行接入构建缓存。

### 6.2 区分错误与提示

保留构建阻塞错误；将 `ASSEMBLY: partial`、`UNCHECKED`、`RUNTIME: not-run`、不影响正确性的性能建议明确标为覆盖范围或提示。

不能为了消除这些输出而重复运行、改用几何或增加浏览器检查。

## 7. 验证与收益评估

维护阶段使用固定任务集：

1. 纯几何新场景。
2. 使用已有模型的场景。
3. 仅修改布局。
4. 新增一种对象。
5. 交付源码迁移后二开。

记录输入与输出 token、总耗时、构建耗时、检索/下载/构建次数、首轮构建成功情况、无关文件修改数量、源码交付完整性。

视觉效果由用户查看，不纳入 LLM 自动评分。维护回归不加入普通生成路径。

完成标准：正确性问题关闭，默认流程不增加步骤，局部修改不重复无关工作，复用能力没有损害编辑和二开。

## 8. 实施顺序

1. 修复源码交付、保存说明、检索契约。
2. 修复动画时间语义。
3. 去重文档，补齐局部修改流程。
4. 补充必要的外观预设与取景计算。
5. 评估组合复用试点。
6. 清理遗留缓存并做维护回归。

先完成前 3 项再评估收益。它们的问题依据最明确；预设和组合库属于有条件的优化，不应与确定的 bug 修复捆绑成一次大改。
